# ScanGrade - AI Agent Context

## Goal
- Complete notification system with WhatsApp-like percakapan (threaded 1-on-1 chat), pengumuman (broadcast), and UU PDP data retention compliance, with strict RBAC separating student↔teacher messaging (no inter-student conversations or broadcasts).

- **The cost of a page is its round-trips, so a row is asked for once.** Supabase answers in ~100-165 ms from this box, and the *cold* student dashboard issued **12** calls: `profiles` four times (three of them for a `class_id` the session already carried), `submissions` three times over the same rows (the row carries `status`, so the "answered" and "retracted" sets come from one read), `teacher_assignments` counted twice with an identical filter where the second answer overwrote the first, and `schools` twice for columns no template renders (`base.html` reads `g.get('school_info')`, which nothing ever sets — the dashboards' `school_info` was dead data, and the per-school favicon has never activated). It is now **6**, and the exam list went 4 → 2. `app/utils/req_cache.py` holds the two lifetimes that make that possible: `memo()` for this request only, in `g` so it cannot leak into the next (the dict it replaced was keyed by `id(request)` and never evicted — it grew for the life of the worker and could serve another request's row), and `ttl()` for rows identical for everyone in a school (name, logo, feature flag, classes, subjects, subject count, a class's active whiteboards), which is what turns 500 students into one query per TTL instead of five hundred. `class_id` rides on the cached session, so no student page reads `profiles` for it. Every writer invalidates what it changed, and `tests/unit/test_round_trip_budget.py` fails if an `invalidate_*` helper loses its call site, if a duplicate query reappears in the two hot routes, or if `id(request)` returns as a cache key

- **The i18n sweep reads card bodies, not just text nodes.** A card here is usually an Alpine binding — `<p x-text="t('Total','Total')">`, or a value out of `x-data` that a later `x-text` renders — and the original check read only `>text<`, so an entire untranslated card passed. The sweep now also reads the *string literals* inside text-rendering bindings (`x-text`, `x-html`, `title`, `placeholder`, `aria-label`, `alt`, `value`), inside `x-data`, and inside every `<script>` (alerts, status lines, `.textContent` writes). Three things make that honest rather than noisy: Jinja is **blanked before reading** (a text node containing `{{ }}` never matched the old pattern at all, and a `t()` whose argument holds a Jinja ternary had its pair split in half); an Indonesian literal counts as translated only when its partner is adjacent — the three shapes this app writes are `t('id','en')` / `sgT('id','en')`, `['id','en']`, and `{ id/en }` or `{ badgeId/badgeEn }` keys — and the partner must look English, so `['Simpan','Batal']` is still an offender; and a literal that is a path (`/api/…`) or a role slug (`guru`, `murid`, `admin_sekolah`) is data, the same string in both languages. `label` and `para` were removed from the marker set for the same reason: both are English words used as code here (`k.label`, `para_`, `p.append('label',…)`), and a guard that fails on code gets deleted. Adding card vocabulary (`aksi`, `tersedia`, `tren`, `penalti`, `mulai`, …) is how the five dashboards were found to be untranslated in the first place

- **Translation progress is a number now, and the deploy refuses to let it go backwards.** "30 pages are translated" said nothing about the other half, and the sweep only reads the pages someone already listed — so the backlog was invisible and invisible progress is how it goes backwards. `deploy/i18n_coverage.py` computes, per template, **pairs / (pairs + leftovers)**: the bilingual units it carries over the copy that still needs to, where a pair shape is `t('id','en')` / `sgT(…)` / a `lang === 'en' ? … : …` ternary / an `['id','en']` array with an English partner / an `{id/en}` or `{badgeId/badgeEn}` key. A pair is a numerator and **never** a denominator (counting a translated string as both is how a coverage number flatters itself), a template whose copy is all shared vocabulary is 100% and not 0%, and emails and role slugs are data. Measured today: **115 templates, 1593 bilingual units, 1376 leftovers — 53.7% overall, 38 templates with nothing left to translate, and 49 with no version in the other language** (`compliance/privacy.html` alone holds 216 strings). Two floors, because a percentage alone can be gamed: `pairs` never falls (exact — bilingual units are not deleted) and coverage never falls by more than `PCT_SLACK = 0.5` pp (one new untranslated string on a 200-unit page). Exit codes follow the other gates: 0 pass · 1 a page translates less · 2 could not measure — a template with **no recorded floor** is 2, not 0, so a new page's number cannot quietly start at zero, and a page that is *newly* frozen (pinned to Indonesian while carrying pairs, which makes those pairs dead — 32 templates are in that state today and it is reported, not failed) is 1. `--write-baseline` records the floors and is deliberately **never run by the deploy**: a gate that raises its own floor while a release is passing makes the regression the new yardstick, and writing inside the checkout mid-deploy would leave the tree dirty for the next `git pull`. Three properties, because the installed path is the only thing the timer runs: it **parses before it installs** (the `@REPO@` placeholder is checked and `bash -n` runs on the staged render *before* the `mv` — a launcher that cannot run is strictly worse than a stale one, since then nothing can deploy at all, and every failure leaves the installed file exactly as it was); the install is **atomic** (staged in the target's own directory, so `mv` is a rename on one filesystem and no tick can observe a half-written file); and it is **skipped when the bytes match**, because Gate 0 compares *content*, so an mtime that moved with no content change would be a signal that lies. It **cannot take a release down with it** — the app is verified and serving by then, so a failure is logged and nothing else happens, and putting `HEALTHY=0`/`FAIL_REASON`/`quarantine_write` in this block would trade a working site for a bookkeeping fix (and quarantine a good commit) — and it does **not** run on the rollback path, where the checkout is about to move back and a launcher installed there would point at logic that no longer runs. The helper reads its target through a global (`LAUNCHER_TARGET`) rather than a parameter, the same choice the quarantine block makes, because `test_deploy_script_takes_no_arguments` forbids reading root's argv *anywhere* in that file. - **The answer sheet is read by asking "is there a 6 mm square of ink centred here?", not by segmenting the photo and hoping the blob survives.** `omr_service.py`'s contour detector was replaced by a matched filter — the mean of a square window minus the mean of a square ring around it, over a ladder of window sizes — because measurement retired the contour version: on a hard simulated phone photo all four corner markers *were* found, within 1.8 px of their true centres, but at ranks **0, 10, 64 and 226** with measured sides of **74, 41, 33 and 47 px against a real 47**. - **`RETR_EXTERNAL` returned zero marker candidates on every photographed sheet.** Every dark mark is inside the page, and a photographed page has a bright closed frame where paper meets desk, so the frame was the outermost contour and every mark on the sheet was one of its holes — never returned. (Kept as a rule because it is the failure mode of any contour search over a photo: *when the page is an object lying on something, the outermost contour is not the page.*)
- **A discarded binary: `Otsu` over an illumination-divided copy, with the blur σ = max/6.** That σ estimates the lighting over a window nearly as wide as the page, so the estimate barely varied where the lighting did, and the clip to 190 pulled paper and desk to the same value — the result's histogram had paper in a broad band around 170 and the desk right beside it, Otsu split *the band* rather than the marks, and `_square_candidates` saw nothing at all. - **Marker selection is anchored on the convex hull of marker-*plausible* candidates, and "plausible" is load-bearing.** Ranking candidates by how dark they look and taking the top 14 put the bottom-left marker at rank **34 of 61** under an uneven light — a gradient across the page lowers a marker's absolute contrast below that of the filled bubbles in the bright half — so the true four were never considered together and the search returned a rectangle of four filled bubbles, 1344 px from the page. The four markers are at the page's own corners, so they are the extreme points by construction; but the hull must be taken over blobs that already pass the quiet-zone test, because a sheet on a *darker* surface produces a bright closed edge that is a row of candidates **outboard of the bottom markers** — measured on a flat scan on a grey desk, the hull of all 45 candidates had 7 vertices, three of them desk edge, and the two bottom markers were **inside** it.

It rejected photographs whose markers were correct to **1.7 px** and whose answers came back **44/44 with 0 wrong**, because a 55%-darker corner and real perspective push a legitimate page to 1.46. And it had no power against the thing it was aimed at: four filled bubbles mistaken for markers also measure **1.23–1.47**, *below* the very line that was rejecting good sheets. `grid_match` — the fraction of bubbles whose **printed outline** is where the model says it is — replaces it, and it is the only test here that checks the whole sheet rather than four points on it. - **A mark scheme is per question *type*, and the paper totals exactly 100 — but a paper that already has marks keeps them.** The two-pool model (objective% / essay%, split equally inside each pool) could not express a scheme a teacher writes down: every objective question got the same marks whether it was a one-line true/false or a four-pair matching item, three essay questions behind 70% were 23.33 each so the paper totalled **99.99**, and every objective question was all-or-nothing — a four-pair matching question answered three ways right earned **nothing**. `app/services/mark_scheme.py` now prices each *type* (`{mcq: 1, true_false: 1, match: 3, drag_drop: 3, essay: 10}` by default, teacher-editable) and scales the paper to exactly 100 by **largest remainder in whole 0.1 steps**: rounding each share on its own is what produces 99.9/100.1, so the leftover steps go to the values that lost the most. `question_types.part_factor` awards the share of a matching question's *pairs* (or a drag & drop's *positions*) that are right, compared against the key's own items so a right pairing given twice with a distractor cannot earn twice. **The scheme rides inside `question_weights` under `_scheme`** (`question_types.SCHEME_KEY`), which is what makes the freeze possible rather than aspirational: a result is *recomputed from stored answers* at publish time and whenever marks are recalculated, so a rule applied to every paper would move marks already in students' hands. An exam with no `_scheme` is scored by the shipped expression — asserted against that expression written out in the test, not described — and awards no part-marks; the builder only writes a scheme when a teacher uses one, so opening and saving an old exam changes nothing. `earned_points` reads the flag off the weights it already receives, so all four scoring sites became scheme-aware with no signature change. The builder's per-type editor carries a **JavaScript copy** of the arithmetic so the total moves while a teacher types — and it is only ever a preview: both exam-saving routes call `_apply_mark_scheme`, which recomputes the marks in Python from the scheme and ignores what the page posted, so a stale page or a form edited in devtools shows a wrong total rather than writing one. A scheme stored by hand in the console that names only some types keeps the rest (`weights_for` merges the stored one in; without that merge an unmentioned type silently falls back to its default). The marking page, the student's result and the printed sheet all show *earned of total* — through `q_part_factor`/`q_partial_credit`, which are the scoring functions themselves exposed as Jinja globals, checked by identity — and a partly-right answer is amber, not red. Two things the work found: `teacher/grade_detail.html` **pins Indonesian by design**, so a `t()` pair added there is dead copy the language gate refuses (it is plain text now); and the gate's own floor had to be re-recorded because `student/result_detail.html` gained a pair. Guards: `tests/unit/test_mark_scheme.py` (37 tests — exactness over 1..80 questions × 5 mark values, the 99.99 arithmetic stated as arithmetic, part-marks including distractors and doubles, the freeze matrix compared against the shipped expression, the route ignoring the page's numbers, the console-partial merge, the pages routing through the scoring functions, and the Python and JavaScript implementations run over the same inputs) — mutation-checked, **7/7 injected defects caught**, the first run having missed one (`weights_for`'s merge) until the test used a *partial* stored scheme, which is the only shape that exercises it.

- **One divisor for a partly keyed paper: the paper's objective questions, not the answers the key happens to hold.** Six places computed a submission's auto-graded score in four ways, and two of them — the scanner's save routes and the Celery OMR task — divided by `objective_key_count`, so a teacher who had keyed **2 of 10** and scanned one sheet was shown `2 / 2 = 100%` for a paper that was two-tenths marked, while the same pupil's online submission stored the *weighted* objective marks and the teacher's own "recalculate scores" wrote `2 / 10 = 20%` to the same column: three numbers for one sitting, chosen by which button was pressed. `question_types.objective_result` is now the one rule — `score = correct / (objective questions on the paper) * 100`, an objective question with no key scored **wrong** (the safe direction, and what `_needs_answer_key` already told the teacher), so a partial key *depresses the ceiling* instead of inflating the score; `ObjectiveResult` carries `correct`, `out_of`, `keyed`, `unkeyed` and a `ceiling` property so a page can put the shortfall in a number.
